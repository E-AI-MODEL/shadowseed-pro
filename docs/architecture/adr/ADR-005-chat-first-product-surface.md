# ADR-005: Chat-first product surface for Shadow Seed Learning

Status: Accepted
Date: 2026-08-18
Owners: Shadowseed maintainers

## Context

Shadow Seed Learning is intended to operate inside a normal conversational LLM experience. A tester should not have to construct a benchmark suite, author a baseline answer, prepare fixture artifacts, or understand research harness internals before they can experience SSL.

The repository currently contains several distinct surfaces:

1. the canonical `ShadowChatSession` runtime;
2. a local Workbench UI;
3. evaluation and benchmark harnesses;
4. historical baseline/result artifacts used for regression and research.

These surfaces serve different purposes. Treating the benchmark/evaluation surface as the product surface creates the wrong user contract.

The product question is simple:

> What is it like to use the same chatbot/model with Shadow Seed Learning active, and how does that differ from the same model without SSL?

That question must be answerable from an ordinary chat UI.

## Decision

### 1. The primary product experience is chat

The default tester experience is a persistent multi-turn chat session using the canonical live runtime:

- `runtime_mode = live`;
- Gate policy = `evidence_backed` unless an explicit research mode says otherwise;
- one visible answer per normal chat turn;
- normal conversation history;
- detected candidates begin weightless;
- only Gate-authorized, point-of-use-allowed seeds may influence a later answer.

The UI must look and behave like a normal chatbot first. Seed inspection, evidence submission, diagnostics, exports and research controls are secondary surfaces.

### 2. Testing SSL off is a product capability, not a fixture requirement

A tester may choose a comparison experience that automatically produces a control answer from the same user prompt and model configuration.

The tester does not provide a baseline answer.

The control answer is generated by the runtime without Shadowseed influence. The SSL answer is generated by the comparison runtime with the same model and conversation context, subject to the SSL Gate and point-of-use rules.

The existing `evaluation` runtime may remain the mechanism for this controlled per-turn comparison, provided the UI labels it as **Compare SSL on/off** or **Research comparison**, not as the normal chat mode.

This comparison is a controlled research/product diagnostic. It is not the default conversation history model for ordinary live use.

### 3. Historical baseline artifacts are research/regression material

Pre-authored baseline fixtures, old benchmark outputs and earlier result artifacts remain useful for:

- regression tests;
- reproducibility;
- historical comparison;
- harness validation.

They are not inputs required from ordinary testers and they are not the definition of the no-SSL product experience.

Where documentation could imply otherwise, these artifacts must be labelled `legacy`, `historical`, `fixture`, `research`, or `regression` as appropriate.

The *concept* of a baseline is not legacy. A baseline remains a valid control condition when it is generated automatically from the same model/configuration for a comparison.

### 4. Product modes are user concepts; runtime modes are implementation concepts

The ordinary UI should expose experience-level choices such as:

- **Chat with SSL** — normal live experience, recommended/default;
- **Compare SSL on/off** — automatically generated control versus SSL-assisted output;
- **Advanced / Research** — raw runtime controls, scenarios, blind review and benchmark tooling.

Raw `live` / `evaluation` terminology may remain in advanced diagnostics and persisted metadata, but it should not be the main onboarding decision.

### 5. High-end model capability is orthogonal to SSL authority

The product may use local or hosted high-end models. Model capability does not grant seed authority.

For every model tier:

```text
candidate -> weight 0 -> evidence / falsification -> Gate -> point-of-use -> optional influence
```

The UI may make high-end providers easy to select, but it may not bypass evidence boundaries, contradiction handling, the Gate, or point-of-use checks.

### 6. Research harnesses remain valuable but subordinate

Capability-scaling suites, blind packets and result bundles remain necessary scientific infrastructure. They measure the system; they are not the user-facing system.

A production-readiness claim therefore requires both:

1. a usable chat-first product surface; and
2. research/operational evidence behind it.

Passing benchmark suites alone cannot satisfy the product requirement.

## Consequences

### Required product changes

- Workbench/new tester sessions default to live/evidence-backed behavior.
- The main Workbench screen is a chat surface, not a scenario runner or JSON console.
- The UI offers an automatic SSL-on/off comparison mode without authored baseline files.
- Raw turn/session JSON moves behind an advanced diagnostics affordance.
- Scenario import and benchmark-oriented flows are explicitly marked Research/Advanced.
- Legacy fixtures remain backward compatible and continue to test historical contracts.

### Compatibility

Existing persisted sessions keep their recorded `runtime_mode`. A missing runtime mode in an old persisted record continues to be interpreted as `evaluation`; changing that fallback would silently reinterpret historical data.

Changing the default for **new** sessions to `live` is therefore safe and intentional while legacy restoration remains stable.

### Non-goals

This ADR does not by itself make the current Gradio preview a hostile-network multi-user service. Authentication, tenancy, TLS, CSRF protection, rate limiting, retention/deletion controls, abuse controls, monitoring and signed standalone packaging remain separate production-hardening work.

## Acceptance criteria

1. A fresh tester can open the product, create a session and chat without supplying a suite or baseline artifact.
2. New ordinary sessions default to live/evidence-backed behavior.
3. The user can select **Compare SSL on/off** and receive automatically generated control and SSL outputs for their own prompt.
4. Ordinary feedback remains record-only.
5. Verified evidence remains an explicit trust action available only on live sessions.
6. The UI cannot edit seed weight/status/promotion directly.
7. Existing legacy evaluation sessions and regression fixtures remain readable and reproducible.
8. Tests prove that legacy missing-mode restoration still resolves to evaluation while new-session defaults resolve to live.
